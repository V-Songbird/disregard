How scoring works

Findings about the wording of an instruction, with the context still yours to review.

From file to findings

The file is read in your browser. The reader parses Markdown, preserves source lines, selects excerpts for isolated scoring, and marks recognized context dependencies. Nothing is sent for scoring until you ask for the prompt.

Eligible excerpts are submitted separately. Each request checks the language, screens for text that tries to redirect the evaluator, and combines local wording checks with model judgments. An excerpt can receive several findings or none.

File input accepts up to 64 KiB and 512 structural blocks. The first 150 ready excerpts are scored. A scored excerpt can contain at most 2000 JavaScript string units. Later excerpts, context-dependent ones and oversized ones remain visible as unreviewed text.

What the factors mean

  • Verb strength (F1). Recognized verbs and phrases describe how strongly an action is stated. A preference can be deliberate; making it mandatory would change its meaning.
  • Prohibition framing (F2). A local check looks for a prohibition and an allowed alternative. Some prohibitions are complete on their own.
  • Trigger distance (F3). A model judges when an instruction becomes relevant and whether that occasion is explicit. Standing requirements can be valid without a named event.
  • Concrete anchors (F7). Local patterns recognize paths, tools, quantities, and other concrete targets. A missing match does not prove that an instruction is unclear, so a model also judges whether someone could check that the instruction was followed; the finding needs both.
  • Enforceability (F8). A model judges how much a deterministic tool could check. Lower values indicate more mechanical coverage; higher values indicate a greater need for judgment.

Additional model questions distinguish instructions from background and suggest a possible home: a standing rule, an event-driven hook, a task-specific skill, or a separate review pass. These suggestions require checking against your project.

Reading a finding

Findings identify something to inspect. They are not an overall grade, a probability of compliance, or an instruction to maximize every factor. Model values can vary between requests, especially near a decision threshold.

Before acting, check the original intent and surrounding conditions. Keep preferences as preferences, preserve valid prohibitions, and verify a replacement tool's coverage before removing the instruction it would enforce.

A clean result means that none of these checks produced a finding. It does not establish that the file is complete, correct, or likely to be followed.

What the refactoring prompt carries

The prompt is built locally from the reviewed snapshot. It carries source locations, scored evidence, and a list of ranges that remain unreviewed. Copying it does not make another model request.

Your receiving agent must read the current file, reconcile findings with its context, and preserve the intended requirements. Review the resulting changes before accepting them.

What still needs context

Excerpts are scored independently and in English. Disregard does not produce a file-wide judgment about contradictions, precedence, duplication, or completeness. Extraction and language screening use heuristics and can make mistakes. A heading can affect an excerpt's meaning without being recognized as a condition.

The interface has six languages, but translated interface text does not make scoring multilingual. Refused, failed, skipped, and context-dependent excerpts contribute no scored advice to the prompt.

The source code includes the current criteria and thresholds. The API reference describes the factor ranges, screening states, and request contract.
